FEL mode runs from BootROM, which only has access to cpu sram (a few kilobytes), it does not initialise the storage controllers (emmc, nand, spi nor) or system dram.
bootrom (boot read-only memory) is a piece of firmware stored in the non-volatile memory directly on the soc that serves as the first code executed by the processor upon being powered on.
with the sunxi-tools utility, we can communicate to the device while its in fel mode, but since the bootloader has not ran, (since we forced fel mode instead of it running the bootloader)
no storage controller are initialised so we cannot interface with the storage.

generalised boot sequence:
step 1 - BootROM / BROM:
the silicon boot read only memory, hardcoded directly into the processors internal mask rom inside the allwinner A33 chip at silicon manufacturing time, it cannot be modified or updated.
when power is supplied to the SoC the arm core jumps to address 0xffff0000 (FEL mode: 0xffff0000, eGON.BRM: 0xffff4000) of the internal boot rom (BootROM) and starts executing instructions.
this is the lowest level firmware on the SoC itself, it initialises tiny internal registers and a small scratchpad of internal SRAM, checks if the FEL pin is low (specific FEL button sequence)
to enter FEL mode (allwinners usb-based low-level recovery and flashing protocol), if normal boot proceeds it probes the primary external storage media
(on a android tablet this is typically internal NAND flash or eMMC) by reading the first few sectors looking for a valid allwinner boot signature.
step 2 - Boot0 (SPL / Second Program Loader):
since the bootrom only has access to the chips small internal SRAM (which is not big enough to hold a full bootloader), it loads Boot0 (also known as the secondary program loader or SPL).
Boot0 is stored in the actual flash memory / storage, we are no longer reading from the soc. it lives in the raw sectors at the very beginning of the storage,
typically starting around offset 8KB / sector 8, before any partition table exists, although this varies.
Boot0s primary job is to initialise more of the hardware like external system RAM (DDR3/DDRL memory). once external RAM is alive and stable, boot0 has a workspace large enough to hand off
control to the next stage.
step 3 - Boot1 (Main Bootloader) + script.bin:
next we have the bootloader which is the last step in initialising the device in preperation for the kernel + OS.
it is loaded by Boot0, its stored following Boot0 at the start of device storage, along with a companion configuration file named script.bin.
the bootloader, this one being propietary by Allwinner, is a fully featured minimal operating system designed for the main hardware initialisations.
it reads script.bin, which tells the bootloader critical board-specific details for the exact device model (eg, pin multiplexing, voltages, power management IC configurations,
the exact display timings, ect). it initialises secondary peripherals (storage controllers, USB, display output, ect). it looks at the flash partition table, locates the Android boot partition,
and copies the linux kernel and its initial ramdisk from flash storage into the system RAM.   
step++ - Linux Kernel + Android:
the bootloader loads the linux kernel image alongside a root filesystem ramdisk, then after the kernel initialises it runs /init which starts initialising android, i dont really care about this.

since we need the bootloader to run in order to initialise all the storage stuff needed for us to make a dump, but we dont want to go into the bootloader since that will just load android,
we need something else to do the storage driver initialisation stuffs for us, that we can also communicate with.
now the process varies depending on the type of storage, looking at the actual chip and searching it up it is a 8GB Parallel MLC NAND Flash chip by sandisk.

once the linux kernel boots, it loads the native allwinner NAND controller driver, reads the hardware specific ECC (error correction code) automatically, and allows tools like nanddump to cleanly
stream a raw image of the flash without fighting uboot configurations plus limitations.

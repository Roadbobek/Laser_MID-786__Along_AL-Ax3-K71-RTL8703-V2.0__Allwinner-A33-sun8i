generalised boot sequence:
step 1 - BootROM / BROM:
the silicon boot read only memory, hardcoded directly into the processors internal mask rom inside the allwinner A33 chip at silicon manufacturing time, it cannot be modified or updated.
when power is supplied to the SoC the arm core jumps to address 0xffff0000 (FEL mode: 0xffff0000, eGON.BRM: 0xffff4000) of the internal boot rom (BootROM) and starts executing instructions.
this is the lowest level firmware on the SoC itself, it initialises tiny internal registers and a small scratchpad of internal SRAM, checks if the FEL pin is low (specific FEL button sequence)
to enter FEL mode (allwinners usb-based low-level recovery and flashing protocol), if normal boot proceeds it probes the primary external storage media
(on a android tablet this is typically internal NAND flash or eMMC) by reading the first few sectors looking for a valid allwinner boot signature.
step 2 - Boot0 (SPL / Second Program Loader):
since the bootrom only has access to the chips small internal SRAM (which is not big enough to hold a full bootloader), it loads Boot0 (also known as the secondary program loader or SPL).
Boot0 is stored in the actual flash memory / storage, we are no longer reading from the soc. it lives in the raw sectors at the very beginning of the storage,
typically starting around offset 8KB / sector 8, before any partition table exists, although this varies.
Boot0s primary job is to initialise more of the hardware like external system RAM (DDR3/DDRL memory). once external RAM is alive and stable, boot0 has a workspace large enough to hand off
control to the next stage.
step 3 - Boot1 (Main Bootloader) + script.bin:
next we have the bootloader which is the last step in initialising the device in preperation for the kernel + OS.
it is loaded by Boot0, its stored following Boot0 at the start of device storage, along with a companion configuration file named script.bin.
the bootloader, this one being propietary by Allwinner, is a fully featured minimal operating system designed for the main hardware initialisations.
it reads script.bin, which tells the bootloader critical board-specific details for the exact device model (eg, pin multiplexing, voltages, power management IC configurations,
the exact display timings, ect). it initialises secondary peripherals (storage controllers, USB, display output, ect). it looks at the flash partition table, locates the Android boot partition,
and copies the linux kernel and its initial ramdisk from flash storage into the system RAM.   
step++ - Linux Kernel + Android:
the bootloader loads the linux kernel image alongside a root filesystem ramdisk, then after the kernel initialises it runs /init which starts initialising android, i dont really care about this.

the usb (micro-usb) port on mobile devices is an OTG (on-the-go) port.
meaning it switches role depending on if the otg ID pin is floating (unconnected) or grounded.
if the pin is grounded the MUSB controller instructs the port to work in host mode, it supplies power to peripheral connected to it like a mouse, keyboard, usb drive, ect.
if the pin is floating, ungrounded, the port works in device/peripheral mode, now the usb port acts as a peripheral so it can be connected to and used by other devices like a computer.
this is why uboot says "No host cable detected".
even if you connected an otg adapter which could force the device into being the host, i think uboot would still say "No USB controllers found".
when the tablet boots normally, the bootloader talks to the AXP223 power management IC (PMIC) to power up the internal clocks, voltage regulators (like reg_dldo1), and the usb physical layer (PHY).
when booting via sunxi-fel uboot, it only loads the bare minimum code and drivers needed to wake up the dram. The usb controller hardware and its power rails remain uninitialized and unpowered.
when uboot's usb initialization routine runs, it scans the memory map for active usb controllers, it finds nothing responding (because they have no power or clock signal),
so it aborts with "No usb controllers found".
not only that the port is stuck in device mode, but the port itself is unusable since the usb controller hardware lacks power and clock initialization since the pmic sequence was not executed.

for the first fix, the simplest one, uboot can leave the usb ports, usb phy / usb musb, in a stale state by not asserting the reset lines before booting kernel.
so i added an assert plus a short delay before the pre-existing deassertions inside the phy (drivers/phy/allwinner/phy-sun4i-usb.c) and musb (drivers/usb/musb/sunxi.c) drivers.
but there is an interesting hardware quirck with some allwinner socs, with socs with the .needs_phy2_siddq flag, they need phy2 to be up and deasserted with SIDDQ cleared for the other phy interfaces
to work. so on these chips, our assertion within 'phy / phy-sun4i-usb.c : sun4i_usb_phy_init' would run on phy2 and since the other phy interfaces rely on its circuitry, for the wait between the
assert and deassert and until SIDDQ is cleared, the other phy interfaces would go down, which could cause serious issues, and if the deassert on phy2 fails for eg the other ports can all stop working
completely. even during a normal boot the usb controllers do not all run sun4i_usb_phy_init at the exact same instant, they probe one after another (or asynchronously in arbitrary order),

so if the bootloader left phy2 dirty / in a stale state phy2 would continue to keep the other phy interfaces working but it itself would not function.
now while this might be rare, only effecting socs with the needs_phy2_siddq flag true (which is just the sun50i h616) with the combined bootloader / sub-linux issue.

to really fix this issue we need to assert each phy within sun4i_usb_phy_probe, this runs once when the phy driver loads, before any usb controller has called phy_init().

    usb/phy: sunxi: Assert reset before deasserting on init

    When a bootloader such as U-Boot (for example with
    CONFIG_USB_MUSB_HOST=y) initializes USB host mode and boots Linux
    without stopping USB first, both the MUSB controller and USB PHY
    reset lines are already deasserted when Linux probes them.

    Because reset_control_deassert() alone is a no-op on an already
    deasserted reset line, stale hardware register state persists across
    boot. On Allwinner A33, MUSB stays wedged in a_wait_bcon with
    DevCtl=0x99, Power=0xf0, and a frozen Frame counter even across
    hot-unplug and replug.

    This series ensures both the MUSB controller and USB PHYs are reset
    cleanly regardless of prior bootloader state, and fixes a related
    PHY2 clock reference imbalance spotted during review:

    - Patch 1 uses devm_reset_control_get_exclusive() and briefly asserts
      glue->rst in sunxi_musb_init().
    - Patch 2 uses devm_reset_control_get_exclusive() and asserts all PHY
      resets in sun4i_usb_phy_probe() before registering the PHY provider,
      avoiding disrupting shared PHY2 on SoCs with needs_phy2_siddq.
    - Patch 3 fixes a pre-existing phy2->clk2 reference imbalance in
      sun4i_usb_phy_init() on SoCs with needs_phy2_siddq.

    Tested on an Allwinner A33 Q8 tablet (Laser MID-786).

  [PATCH v2 1/3] (93ffdd67b7b2)
    usb: musb: sunxi: Assert reset before deasserting on init

    When a bootloader such as U-Boot (for example with
    CONFIG_USB_MUSB_HOST=y) initializes MUSB and boots Linux without
    stopping USB first, the controller reset line is already deasserted at
    probe time.

    In that case reset_control_deassert() in sunxi_musb_init() is a no-op
    and stale MUSB register state persists across boot. On Allwinner A33,
    MUSB stays wedged in a_wait_bcon with DevCtl=0x99, Power=0xf0, and a
    frozen Frame counter even across hot-unplug and replug.

    Request exclusive reset control via devm_reset_control_get_exclusive()
    and assert glue->rst briefly before deasserting it when
    SUNXI_MUSB_FL_HAS_RESET is set so MUSB starts cleanly.

    Tested on an Allwinner A33 Q8 tablet (Laser MID-786).

    Fixes: 132e23775779 ("usb: musb: sunxi: Add support for musb controller in A31 SoC")
    Signed-off-by: Bobek Brzeczyszczykiewicz <admin@roadbobek.com>

  [PATCH v2 2/3] (924dce22113d)

    phy: sun4i-usb: Assert PHY resets in sun4i_usb_phy_probe()

    When a bootloader initializes USB before booting Linux without first
    tearing down the controller, phy->reset may already be deasserted when
    Linux probes the USB PHY driver.

    Because reset_control_deassert() alone is a no-op on an already
    deasserted reset line, stale USB PHY state can persist across the
    bootloader-to-kernel handoff. Asserting phy->reset inside
    sun4i_usb_phy_init(), however, could disrupt active PHYs on SoCs with
    needs_phy2_siddq (such as the Allwinner H616), where PHY0, PHY1, and
    PHY3 depend on PHY2 remaining out of reset once enabled.

    Request exclusive reset controls via devm_reset_control_get_exclusive()
    and assert all PHY resets in sun4i_usb_phy_probe() before registering
    the PHY provider so every PHY starts from a clean reset state before
    any consumer calls sun4i_usb_phy_init().

    Tested on an Allwinner A33 Q8 tablet (Laser MID-786).

    Fixes: ba4bdc9e1dc0 ("PHY: sunxi: Add driver for sunxi usb phy")
    Signed-off-by: Bobek Brzeczyszczykiewicz <admin@roadbobek.com>

  [PATCH v2 3/3] (375d39618a19)

    phy: sun4i-usb: Fix phy2->clk2 reference imbalance in sun4i_usb_phy_init()

    In sun4i_usb_phy_init(), the needs_phy2_siddq path enables phy2->clk2
    to access the REG_HCI_PHY_CTL PMU register for PHY2, but then disables
    phy->clk2 instead of phy2->clk2.

    This leaks a prepare/enable reference on phy2->clk2 while prematurely
    disabling phy->clk2, causing a clock disable/unprepare underflow when
    sun4i_usb_phy_exit() later runs.

    Disable and unprepare phy2->clk2 instead of phy->clk2.

    Fixes: b45c6d80325b ("phy: sun4i-usb: Introduce port2 SIDDQ quirk")
    Signed-off-by: Bobek Brzeczyszczykiewicz <admin@roadbobek.com>
